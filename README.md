### 1-1. 서비스 정의

| 항목 | 내용 |

**서비스 범위**

취켓은 취소표를 **발견해 알려주는 것까지**를 범위로 한다. 실제 예매와 결제는 각 사업자의 공식 예매처에서 이루어지며, 앱은 알림과 함께 공식 예매처로 연결하는 역할을 한다.

## 3. 설계 근거

### 3-1. 전체 플로우 중 이 3화면을 고른 이유

서비스의 전체 사용자 플로우는 8단계다.

```
앱 진입 → 교통수단 선택 → 기본 일정 입력 → 교통수단별 세부 조건 입력
→ 희망 시간 범위 설정 → 입력 조건 확인 → 모니터링 요청 생성
→ 요청 목록 상태 확인 → 취소표 발생 알림 → 사용자 행동 선택
```

이 중 시안 3장은 **서비스의 가치가 성립하는 최소 단위**를 기준으로 선정했다.

| 화면 | 플로우상 위치 | 이 화면이 증명하는 것 |
|---|---|---|
| 일정 등록 | 기본 일정 입력 | 조건을 **걸어둘 수 있다** |
| 요청 목록 | 요청 목록 상태 확인 | 걸어둔 것을 **지켜보고 있다** |
| 취소표 발견 알림 | 취소표 발생 알림 | 결국 **잡아준다** |

또한 일정 등록은 실제로 4단계 입력 폼이지만, 시안에서는 **1단계만 그리고 상단에 진행 인디케이터를 배치**했다. 4단계를 한 화면에 담으면 요소가 20개를 넘어 이미지 생성 품질이 급격히 떨어지고, 인디케이터만으로도 "여러 단계로 구성된 입력"이라는 정보는 충분히 전달되기 때문이다.

### 3-2. 기능 우선순위

| 우선순위 | 항목 |
|---|---|
| **P0** 필수 구현 | 이동수단 선택, 출발지·도착지 선택, 날짜·인원 선택, 차량·좌석 조건 선택, 시간 범위 설정, 모니터링 요청 생성, 요청 목록 출력, 요청 수정·삭제·일시정지, 취소표 발견 알림, 반응형 모바일 UI |
| **P1** 선택 구현 | 노선 즐겨찾기, 입력값 로컬 저장, 공식 예매처 이동 |
| **P2** 구현 범위 제외 | 실제 코레일·SRT 로그인, 실시간 좌석 크롤링, 실제 예매·결제, 회원가입, 지도, 서버 및 데이터베이스, 실제 푸시 알림 |

시안 단계에서 P2를 명시적으로 배제한 것은 **화면에 그리지 않기 위해서**다. 이미지 생성 AI는 "예매 앱"이라는 입력만으로 로그인 화면, 지도, 결제 카드 UI를 임의로 추가하는 경향이 있어, 프롬프트 단계에서 이를 배제 조건으로 명시했다.


### 3-3. 상태 표현 설계

요청 상태는 5종(`모니터링 중` `취소표 발견` `확인 중` `일시정지` `종료`)이지만, 시안에서는 **5개를 5색으로 구분하지 않았다.**

| 상태 그룹 | 상태 | 색 처리 |
|---|---|---|
| 진행 중 | 모니터링 중, 확인 중 | 【차분한 파랑 계열】 |
| **발견** | **취소표 발견** | 【강조색 1종 — 앰버】 |
| 멈춤 | 일시정지 | 【회색】 |
| 종료 | 종료 | 【옅은 회색】 |

이 화면에서 사용자가 확인하려는 정보는 "내 요청이 잡혔는가" 하나다. 다섯 가지 색이 동등하게 경쟁하면 그 하나가 묻히므로, **`취소표 발견`에만 강조색을 배정**하고 나머지는 무채색과 저채도로 묶었다.
